# Initial firmware analysis: Uptown Automation U7 MI V2.7++

The input is the locally preserved canonical image described in
[`../firmware/README.md`](../firmware/README.md). The binary is intentionally
not duplicated in the analysis tree. Re-run the dependency-free first-pass
analyzer with:

```sh
python3 dyaxis/analysis/analyze_8051.py \
  .local/dyaxis/eprom-dumps/490-0270-MI-V2.7-M27C128/490-0270-MI-V2.7-M27C128.bin
```

## Verified facts

- The image is 16,384 bytes, non-blank, and has SHA-256
  `a29a17def1f51a6475d21da22a93bd9adf2c7c62f984f87c15170c2bd78eb0c3`.
- It is associated with the Uptown Automation Systems, Inc. multichannel
  control/fader automation board in the Dyaxis/MultiDesk surface, socket `U7`,
  with adjacent IC reference `U8`, an Intel/Philips PCB 80C552-5, and a
  24.000 MHz crystal. The sticker transcription remains provisional:
  `MI V2.7++ / 490-0270 / SUM 0F1C`.
- Reset begins with `LJMP 0x1E12` at `0x0000`. The remaining standard vector
  locations are not all simple long jumps in this image, so vector ownership
  needs a control-flow-aware disassembly rather than assuming the U17 layout.
- The first-pass opcode scan finds instruction-shaped writes at offsets
  `0x1CA9` (`MOV TMOD,#0x20`), `0x1CAC` (`MOV TH1,#0xF4`), `0x1CB2`
  (`MOV TCON,#0x40`), and `0x1CB5` (`MOV SCON,#0x52`). These are strong UART
  initialization candidates in the code region, though the complete routine
  still needs disassembly.
- Printable strings include `990 version %bd.%bd, %bd channels%s`,
  `control panel`, `checksum: %04X`, `TEST MODE`, `CHANNEL REMAP ENABLED`,
  `Safe`, `Run mode`, `Sync mode`, `Raw mode`, `Send id`, `Deadman has kicked
  the watchdog!`, RAM-test diagnostics, and `Uptown Automation`.
- The public source image was read three times with the TL866A using the
  approved read-compatible `AM27C128@DIP28` definition. Each read was exactly
  16,384 bytes and the three reads compared byte-for-byte identically.

## Comparison with Studer-Editech U17 V1.06

| Property | Uptown Automation U7 | Studer-Editech U17 |
|---|---:|---:|
| Device image size | 16,384 bytes | 32,768 bytes |
| Device | ST/SGS-Thomson M27C128-12F1 | AMD AM27C256-95DC |
| Reset target | `0x1E12` | `0x2F6F` |
| Early vector layout | Mixed inline code/data-looking entries | LJMP targets for reset, external 0/1, timer 0/1, serial |
| Distinct strings | Control-panel, channel, watchdog and test diagnostics | `MultiDesk Boot ROM, version 1.06, 28-Jun-94` and boot diagnostics |
| Shared printable strings | None found by the first-pass scan | None found by the first-pass scan |

Raw byte-window comparison found shared non-blank 64-byte windows, but no
shared windows of 96 bytes or longer. This is not enough to claim copied code:
the images are 8051-family firmware and may share compiler/runtime idioms or
common short routines, while data/code boundaries have not been recovered.

## Hypotheses and next tests

- The strings and U7 provenance make a multichannel control/fader automation
  role more likely than the U17 boot-ROM role. This is a functional hypothesis,
  not a complete board-level protocol identification.
- The `TMOD`/`TH1`/`TCON`/`SCON` sequence is likely serial initialization. The
  exact baud rate, SMOD state, interrupt setup, and whether the serial path
  reaches RS-422 transceivers require control-flow tracing and captures from
  the board.
- The 24.000 MHz crystal and `TH1=0xF4` should be used as measured timing
  inputs, but no baud-rate claim is made until the P80C552 clocking mode and
  actual link timing are confirmed.
- `Send id`, channel-count formatting, checksum text, sync/raw/run modes, and
  watchdog diagnostics are packet/protocol leads. They do not by themselves
  establish framing, checksum algorithm, or host message semantics.

## Scope boundary

This is a read-only initial report. It distinguishes byte-level evidence from
hypotheses and does not modify either canonical firmware image.
