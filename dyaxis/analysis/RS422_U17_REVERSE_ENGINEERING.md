# U17 RS-422 reverse-engineering report

Date: 2026-09-18. Scope: only the public Studer-Editech U17 image
`41.005.415.Z1-U17-V1.06-AM27C256.bin`, SHA-256
`22aa7788f49abf0c5ad31d0bc15fb2048cacaec1bac8cec0ddde87e29854e0dd`.
The second 16 KiB Uptown Automation image is deliberately out of scope.

## Method and evidence boundary

The image was checked as 32,768 bytes with the recorded SHA-256 before
analysis. `disasm51` 1.0.2, pinned to source commit
`a32d0adc80cfbf203745318900ced5ea94303b15`, performed reachable 8051
control-flow disassembly from every P80C552 vector entry. The generated
assembly is `generated/u17/u17.reachable.asm`; reports are generated by
`report_u17.py`. Exact commands are in `analysis/README.md`.

P80C552 assumptions come from the Philips/NXP overview and datasheet listed in
`SOURCES.md`: SIO0 is the standard full-duplex UART at vector `0x0023`, SIO1
is the I2C interface at `0x002B`, and SIO0 baud generation normally uses
Timer 1. The documented board photo/notes identify a 12.000 MHz oscillator;
the exact crystal marking should still be checked against the U17 board before
using a calculated baud candidate.

The board also contains an identified Xilinx `XC3030TM-70 PC68C` FPGA and a
nearby `PALC22V10L-25PC` programmable PAL (`9353 000020`), plus a photographed
Z85230-family serial controller. See `U17_FPGA_ARCHITECTURE.md`. Consequently,
out-of-image `MOVX`/call targets around `0xFEC0`–`0xFEF9` are treated as an
unresolved external bus/peripheral window, not presumed to be another ordinary
ROM.

The executable-RAM question is now answered separately in
`U17_EXECUTABLE_RAM_LOADING.md`: U17 contains a confirmed receive/XDATA-write/
checksum/`LCALL 0x8000` path. This establishes the loader mechanism but not
the wire framing or a usable host protocol.

## Confirmed findings

- Reset vector `0x0000` is `LJMP 0x2F6F`; reset clears internal RAM, clears
  interrupt enables, initializes external memory/peripherals and transfers
  into startup code including `0x01E0`.
- The P80C552 vector report is in `generated/u17/interrupt-vectors.md`. The
  serial vector `0x0023` is `LJMP 0x3416`; the other observed targets are
  `0x3452`, `0x3470`, `0x33F8`, `0x348E`, `0x34AC`, `0x34CA`, `0x34E8`,
  `0x3506`, `0x3524`, `0x3434`, `0x3542`, `0x3560`, and `0x357E`.
- The `0x3416` serial ISR saves ACC/B/DPTR/PSW, reads `MOVX` external data
  at `0xFED0`, calls external target `0xFED1`, restores context and returns
  with `RETI`.
- Reachable, named P80C552 SFR accesses include `IEN0`, `IEN1`, `IP1`,
  `TM2CON` and `TM2IR`. The boundary-qualified list is in
  `generated/u17/serial-register-xrefs.tsv`.
- No reachable instruction directly accesses `S0CON`, `S0BUF`, `PCON`,
  `TCON`, `TMOD`, `TL0`, `TL1`, `TH0` or `TH1`. This is a verified absence
  from this disassembly pass, not evidence that external serial hardware is
  unused.
- Embedded strings identify `MultiDesk Boot ROM, version 1.06, 28-Jun-94`,
  with boot/checksum and master-reset messages.

## Inferences and unresolved protocol questions

Strong inference: the serial-vector path is a thin interrupt shim around an
external-memory/peripheral service at `0xFED0`/`0xFED1`. Separately, the
`0xFFE1/0xFFE3` path is now more plausibly a local FPGA/PIC mailbox because
new board trace evidence places a PIC between the XC3030 and scanned controls.
Those interfaces must not be combined. Repeated `MOVX` accesses and calls
outside the 32 KiB ROM mean the EPROM alone does not expose enough named UART
state to recover Macintosh packet framing or baud confidently.

Hypotheses requiring a passive wire capture: the external service may be a
serial controller/register window; the ROM may use RAM or external hardware
for RX/TX queues; and the RS-422 protocol may have command/acknowledgement,
length, escaping, retry or checksum fields. No byte offset is promoted to a
packet field until a capture confirms it. Candidate RAM references are listed
in `generated/u17/ram-candidates.tsv`, but are not proven RX/TX buffers.

The 12.000 MHz oscillator is documented, but no valid reachable `TH1`/`TMOD`
initialization was found. Baud is therefore **unresolved**, rather than
guessed from a generic 8051 formula.

## Passive capture gate and next milestone

Do not connect TTL serial hardware to the rear connectors. Before tapping:

1. With the board unpowered, photograph and read the exact RS-422 transceiver
   part numbers, connector pin labels, and PCB trace side. Continuity-trace
   each connector pin to the transceiver A/B pins to establish pair polarity,
   direction and any reference/ground pin. This is the only physical evidence
   still required before selecting adapter wiring.
2. Use a receive-only, high-impedance RS-422 differential receiver/probe with
   no driver enabled. It must expose A/B for each identified pair, tolerate the
   measured common-mode range, and connect reference/ground only as justified
   by the transceiver circuit. Do not add termination until existing
   termination topology is known. Do not attach a single-ended TTL probe to A
   or B.
3. Capture both directions with timestamps while repeatedly pressing one
   physical button. Decode the repeated request and reply, then test one LED
   or motor-fader command path. Preserve raw capture and derived decoder output
   separately.

The smallest next physical action is a clear, powered-off close-up of the rear
RS-422 transceiver markings and connector/pin side, plus confirmation of the
U17-board oscillator marking if it differs from the documented 12.000 MHz note.

## Future software boundary

Once framing is evidenced, keep the implementation boundary as:

`Dyaxis RS-422 protocol <-> normalized events/state <-> OSC mixer API`

No daemon or protocol implementation is claimed by this report.

For the U17 main-program reconstruction, including reset flow, mailbox
semantics, service-value state transitions and the PIC/FPGA responsibility
boundary, see `U17_MAIN_PROGRAM_ARCHITECTURE.md` and
`U17_HIGH_ADDRESS_MAILBOX.md`.

The critical path is now: reuse existing controller startup/local-control
behavior, identify the physical RS-422 interface, passively reconstruct the
existing command protocol, then bridge normalized surface events/state to OSC.
Replacement 8051 firmware is a fallback only if the existing command
interface cannot be reused.
